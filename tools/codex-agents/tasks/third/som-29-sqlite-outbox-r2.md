## Контекст

База — `fix/som-50-template-picker`, включая `f98423f` (ADR 0061).
SOM-28 уже влита: `supabase/migrations/20261001140000_workout_journal.sql`,
шесть таблиц журнала, revision, owner-only `sync_operations`, приватные заметки.
Не начинать схему заново. Демо-журнал на AsyncStorage не является production
outbox. В зависимостях Linear SOM-53 ещё Backlog, но решение владельца уже
принято и влито: ADR 0061 и закрытые вопросы №3/6/8 — действующий источник.
Linear не менять.

Владелец утвердил: разные ID подходов объединяются с сохранением порядка и
источника; конфликт одного подхода сохраняет обе версии и устройство каждой,
выбирает тренер. Замена упражнения против дописанного подхода и удаление против
правки — по таблице `prototype-fresh/SYNC-DESIGN.md`, без молчаливой потери.
Правка после завершения сохраняется отдельным черновиком исправления;
завершённые данные автоматически не переписываются. Клиент видит только
завершённые журналы, результаты вводит только тренер.

SOM-39 влита PR #23: UI, профиль, типографика, анимации, layout
Today и журнала. Сохрани её изменения; эти файлы вне границ r2. Эта задача создаёт самостоятельный production модуль и его
контракты; подключение к существующим экранам, предзагрузка SOM-30, полный
production ввод SOM-31 и завершение SOM-32 остаются следующими задачами.

## Критерии

- [ ] Добавить совместимый с установленным Expo `expo-sqlite`, локальную схему
  журнала/outbox и типизированный адаптер. Запись результата и операции
  `{operation_id, kind, entity_id, base_revision, device_id, payload, created_at}`
  происходит одной транзакцией; при ошибке транзакции нет ложного успеха.
  Закрытие и повторное открытие восстанавливают неподтверждённые операции.
- [ ] Аккаунт/workspace изолированы в локальном хранилище, отправке и ответах;
  logout/смена аккаунта не отправляют старую очередь за нового пользователя.
  Не удалять неподтверждённые данные без явного безопасного механизма.
- [ ] Новой миграцией реализовать RPC `apply_operations` поверх SOM-28:
  стабильные ID, проверка роли/tenant/связей, ревизий и payload, owner-only receipts.
  Повтор после потерянного ответа возвращает прежний результат без второго
  применения; повтор operation_id с другим payload отклоняется. Параллельный
  повтор защищён сервером. Детерминированный порядок пачки и частичные ошибки
  документированы; одна ошибочная операция не приводит к потере остальных.
- [ ] Реализовать сохранение обеих версий конфликтного подхода и черновика
  правки завершённого журнала по ADR 0061. Не применять last-write-wins;
  private notes/receipts/черновики не доступны клиенту. Типизированный контракт
  разрешения конфликта явно выбирает версию и проверяет текущую ревизию.
- [ ] Создать transport и runner outbox: только подтверждённые операции
  перестают ожидать отправку; ошибка сети/timeout/потерянный ответ сохраняют
  данные и тот же operation_id для retry. Не допускать параллельных runner,
  бесконечного tight loop и смешивания ответов разных сессий.
- [ ] Экспортировать модель состояния «Сохранено на телефоне» /
  «Синхронизировано» / ошибка / конфликт и отдельный небольшой i18n компонент
  в новом модуле. Существующие экраны не менять; описать точку подключения
  для SOM-30/31. До commit локальной транзакции не показывать «Сохранено».
- [ ] Тесты: rollback локальной транзакции, reopen, порядок, duplicate,
  потерянный ответ и retry, offline→online, три вымышленных участника,
  конфликт двух устройств, поздняя правка finished, stale conflict resolution,
  logout/account switch. Проверять бизнес-инварианты, а не только вызовы mock.
  Для SQL добавить pgTAP на права, приватность, replay/payload mismatch,
  revision/conflict и отдельный воспроизводимый сценарий concurrent replay.
- [ ] Синхронизировать `database.types.ts` с новой SQL API; при отсутствии
  Supabase честно отметить, что генерация/drift-check не выполнены, не выдавать
  вручную добавленные типы за результат генератора.
- [ ] `cd app && npm run check` зелёный. Обновить CHANGELOG и checkpoint ROADMAP,
  ADR/контракт реализации, отчёт `app/review/som-29-sqlite-outbox/README.md`
  с точными командами, результатами и оставшимися проверками. Не объявлять
  SOM-29/этап 5 полностью принятыми по mock-тестам и без устройств.

## Разделение работы

Используй до трёх субагентов по `tools/codex-agents/SUBAGENTS.md`:
серверная миграция/pgTAP; SQLite storage; независимые transport/runner тесты.
До параллельной реализации ведущий фиксирует общий operation/result контракт
и исключительное владение файлами. Ведущий интегрирует runner/component,
владеет package files, database.types, i18n внутри нового модуля и документацией;
финальный npm run check запускает только ведущий.

полёта с тремя участниками и чтением со второго устройства — не проверен здесь.

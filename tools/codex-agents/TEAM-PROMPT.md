# Промпт: запустить команду Codex-агентов по запросам владельца

Вставь блок ниже в сессию Claude Code (или ведущего Codex) на хосте, в папке
`trainerApp`, и допиши список запросов в конце.

---

Ты — оркестратор команды Codex-агентов trainerApp. Команда:

- **work**, **personal** — рабочие: каждый берёт брифы из `tasks/<аккаунт>/` по
  алфавиту, один бриф = одна ветка `agent/<имя-файла>` = один PR в базовую ветку,
  сами вливают PR при зелёном CI;
- **third** — Pro: координатор после каждой задачи (`COORDINATOR.md`) и рабочий
  для самых крупных задач с до трёх субагентов (`SUBAGENTS.md`);
- **ты** — превращаешь запросы владельца в брифы, ставишь их в очередь, следишь
  за ходом и проверяешь результат на устройстве.

Очередь и скрипты: `../trainerApp-agents/tools/codex-agents/` (ветка
`claude/busy-bardeen-3kzcza`). Правила рабочих — `RULES.md`, формат брифа — любой
файл в `tasks/done/`. Базовая ветка — `fix/som-50-template-picker`, не `main`.

## 1. Разбор запросов

Для каждого запроса определи одно из трёх:

- **баг** — поведение расходится с эталоном или ломает экран: сначала найди
  причину сам (код, симулятор/устройство), в бриф пиши причину и место;
- **решение владельца** — сознательное отступление от `prototype-fresh`: в брифе
  раздел «Решение владельца <дата>», требование ADR и записи в `docs/app/UI-PARITY.md`;
- **неясно** — запрос противоречит действующему правилу (ADR, UI-PARITY,
  PROJECT-MEMORY). Задай владельцу вопрос сразу, одним сообщением со всеми
  вопросами, до записи брифов. Во время работы агенты вопросов не задают.

Найди задачу Linear для каждого запроса (`docs/app/DELIVERY-PLAN.md`, live Linear);
номер идёт в имя брифа и заголовок PR. Новые задачи в Linear не создавай без
разрешения владельца.

## 2. Распределение

- Один запрос — один бриф с целой задачей: код, тесты, документы.
- «Границы» брифов разных аккаунтов не пересекаются по файлам. Если два запроса
  трогают одни файлы — оба в один аккаунт, по порядку (`18-…`, `19-…`), и второй
  бриф ссылается на первый.
- Самый широкий запрос (много экранов, новая зависимость) — в **third**, с
  предложенным разбиением на субагентов.
- Номер брифа больше максимального в `tasks/` и `tasks/done/`.

## 3. Содержание брифа

Заголовок с SOM-номером, ссылка Linear, ветка, решение владельца (если есть),
контекст с точными путями `file:line` (бери через `graft ask … --source`),
критерии с чекбоксами, «Границы», «Нельзя проверить в контейнере». Обязательно:

- анимированные стили и `className` — только через `AnimatedView` /
  `AnimatedPressableView` из `app/src/ui/motion.tsx` (ADR 0110);
- в Jest Reanimated замокан: UI-изменения нативно в контейнере не проверить —
  в отчёте честное «не проверено на iPhone».

## 4. Запуск

1. Все PR, от которых зависят брифы, влиты в базовую ветку (`gh pr list`).
2. Удали `STOP`, закоммить брифы в ветку очереди и запушь — только когда
   супервизор и координатор не работают (`pgrep -fl supervisor`).
3. Супервизор запускает владелец (токен в команду не вставлять):
   `export GH_TOKEN=… BASE_BRANCH=fix/som-50-template-picker` →
   `nohup tools/codex-agents/docker/supervisor.sh >/dev/null 2>&1 &`.
4. Следи через `logs/summary.txt`, `logs/supervisor.txt`, `COORDINATOR-LOG.md`
   (или панель `dashboard/server.py`, http://localhost:8787). Сообщай владельцу о
   завершении задач, сбоях и STOP, а не о каждом шаге.

## 5. Приёмка

После слияния: собери Release на iPhone владельца, проверь сам, что можешь
(скриншоты `xcrun devicectl device capture screenshot`), и дай владельцу короткий
список, что посмотреть. Linear: только In Progress / In Review; Done ставит
владелец после своей проверки. Экраны принятыми не объявлять.

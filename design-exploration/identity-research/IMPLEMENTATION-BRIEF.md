# Следующая итерация прототипа: что именно переносить

23 сентября 2026. Спецификация для обсуждения, не выполненное изменение основного прототипа. Источники: действующий handoff, исходный код прототипа, воспроизводимый аудит REPORT.md и изолированное исследование direction.html.

## Граница решения

Внешний язык gymGO уже принят; новый бренд, персонажи и композиции из исследования ещё не утверждены. Исправление фактов и сохранения не должно зависеть от выбора иллюстрации. Ниже разделены функциональные исправления и визуальные предложения. Не переносить исследовательские заглушки, слово «Демо», фиксированные часы и элементы управления сравнением в интерфейс продукта.

## Первый вертикальный сценарий

Тренер открывает текущее занятие → вводит подходы каждому участнику → возвращается к предыдущему участнику → проверяет пробелы → завершает → снова открывает запись → клиент видит фактически записанный результат.

Это важнее расширения библиотеки иллюстраций. Пока сценарий не проходит, нельзя обещать «результаты сохранены» или считать запланированную встречу посещением.

### Запись подходов

Держать программу, черновик и записанный факт отдельно. Пустое поле с предыдущим значением в placeholder — не выполненный подход. Ключ записи должен включать занятие, участника, упражнение и подход, а не только номер строки.

Критерии приёмки:

- Значения Алии не появляются у Мади; при возвращении к Алии оба её состояния — черновик и записанный подход — остаются.
- Изменённая записанная строка снова требует сохранения. Повторное сохранение не создаёт второй подход.
- Подсказка о незаписанных данных проверяет всех участников и все упражнения, а не только текущую вкладку.
- Завершение не очищает результаты. Повторное открытие показывает те же фактические значения.
- Если хранение только в памяти, интерфейс этого не скрывает. Надпись «на устройстве» допустима только после реальной проверки локального восстановления.
- Непришедший участник, пропущенное упражнение и незаполненное поле — разные причины. Не превращать их автоматически в нули.
- Кнопки повторяемого ввода не меньше 48 px по проектному правилу; цифровые поля имеют понятные доступные подписи.

Исследование сейчас моделирует только одно упражнение, двухподходную схему и полное завершение. Это не готовая реализация сценариев отсутствия или частичной тренировки.

### Разные факты, разные состояния

| Сущность | Пример состояния | Что из неё нельзя выводить автоматически |
| --- | --- | --- |
| Запись в расписании | запланировано / отменено | посещение, оплату, выполненные подходы |
| Запрос переноса | ожидает / принят / отклонён | отмену первоначальной записи до принятия |
| Посещение участника | не отмечено / был / не был | одинаковый статус всей мини-группы |
| Подход | черновик / записан / явно пропущен | выполненный факт из placeholder |
| Учёт абонемента | отдельная запись списания | денежный платёж или эквайринг |

Названия — предложение, не новый утверждённый API-контракт. В продакшне правила доступа и конкурентных изменений должны проверяться на стороне сервера; клиентская проверка в исследовании не является защитой.

## Второй вертикальный сценарий: перенос

Клиент предлагает новое время для конкретного занятия → видит исходное и предложенное время → тренер принимает или отклоняет → обе стороны видят одно действующее время.

Критерии приёмки:

- Во всех действиях передаётся выбранное занятие; никакого жёстко заданного `s8`.
- Ожидающий запрос не зачеркивает действующее время и не заменяет ближайшую подтверждённую встречу на главной.
- У обеих сторон показаны полная дата, день недели и интервал, а не только час.
- Клиент не видит кнопки принятия собственного запроса. Отдельное право тренера не должно моделироваться как скрытая «роль» в клиентской шторке.
- Отклонение сохраняет исходное занятие. Оно не отменяет встречу.
- Повторный или устаревший ответ не перезаписывает уже принятое решение. Нужна версия записи или равноценная проверка на сервере после выбора стека.
- Отмена занятия и снятие запроса на перенос — разные действия и разные подтверждения.
- Если исходное занятие отменили, пока шторка была открыта, принять перенос нельзя; нужно показать актуальное состояние.

Последний пункт не воспроизводится в новом узком исследовании: для него нужна отдельная конкурентная фикстура, не вымышленное подтверждение теста.

## Третий вертикальный сценарий: результат у клиента

Клиент открывает ближайшее занятие и историю после действий тренера.

- Отменённые занятия исключены из ближайших активных, но не бесследно удалены из истории.
- Индикатор посещений выводится из фактов посещения, а не из дат расписания.
- История поддерживает персональные и групповые занятия; статус относится к данному клиенту.
- График показывает только сопоставимые измерения, имеет даты и объяснение метрики. Если данных мало, сообщает об этом, а не имитирует стабильный прогресс.
- Клиент может отличить отсутствие данных от нулевого результата и от пропуска занятия.

## Визуальные предложения после функциональных исправлений

1. Привязка Today к текущему/следующему занятию, с доступным раскрытием прошедшей части дня. Не терять ранее исследованные пересечения персональных тренировок.
2. Раздельные поверхности для ближайшей подтверждённой встречи и запроса по другой встрече.
3. Видимые счётчики записи по людям, достаточно крупные поля и действия сохранения.
4. Условная рисованная сцена на приглашении; отдельное реальное имя тренера, без подмены его портрета сгенерированным персонажем.
5. Пустой блокнот только там, где он объясняет следующий шаг. На расписании и записи — без декоративных изображений.
6. Короткая шторка, отсутствие движения на повторяемом вводе и клавиатурных действиях; static/reduced-motion вариант полноценен.

## Ручной прогон перед интеграцией

Делать на свежей фикстуре и повторять без перезагрузки там, где проверяется сохранение. Проверять минимум узкий телефон, обычный телефон и широкое окно; реальные экранная клавиатура и скринридер — отдельный этап.

| Действие | Ожидаемый результат |
| --- | --- |
| Нажать запись пустого подхода | Понятная ошибка у поля, фокус в поле, счётчик не изменён |
| Ввести `8,5` и `12`, записать | Ровно одна запись; понятный сохранённый статус |
| Ввести черновик второго подхода и сменить человека | Черновик остаётся у исходного человека |
| Заполнить только одного из троих и завершить | Названы другие участники с пробелами |
| Заполнить всех, подтвердить, открыть снова | Значения не очищены и не продублированы |
| Открыть перенос клиентом | Видны обе даты, нет кнопок тренера |
| Отклонить тренером | Исходное время осталось, встреча не отменена |
| В свежем сценарии принять тренером | Только целевая будущая встреча получила новое время |
| Быстро открыть/закрыть шторку, нажать Escape | Нет зависшей модальности и скачка из неверной позиции; фокус возвращён |
| Включить reduced motion | Нет перемещения шторки; состояние и действия остаются понятны |

## Что нужно решить до переноса художественного направления

Выбрать между точным расписанием без персонажей и рекомендуемым сочетанием «рабочий реестр + общий блокнот». Решить, нужна ли анимация вообще после просмотра реального размера на телефоне. Проба Seedance не является автоматическим одобрением постоянного видео в приложении.

Новый backend, окончательный нейминг, платёжный провайдер, публикация и маркетинговые обещания не входят в эту итерацию.

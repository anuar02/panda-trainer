# Руководство по прототипу

## Как открыть

Зависимостей и сборки нет — это статические HTML/CSS/JS:

```bash
open prototype/index.html
# или
python3 -m http.server 8000   # http://localhost:8000/prototype/
```

Шрифты Inter/Montserrat включены локально в `prototype/assets/fonts/` вместе
с лицензиями и не требуют Google Fonts. При ошибке загрузки остаются системные fallback.

## Сценарии для проверки

Ниже — как воспроизвести критерии приёмки из handoff v2 (§13).

### Перенос (обе роли)
1. Тренер → Входящие. Видны два запроса. У Айгерим: действует `чт 17 сен 18:00`,
   предложено `пт 18 сен 19:00`, «Ждёт вас».
2. **Принять** → занятие Айгерим переезжает на пятницу 19:00, запрос уходит в историю.
3. Вместо принятия можно **Другое время** → встречное предложение; ответственный
   меняется на клиента.
4. **Отклонить** / **Отозвать** → действует прежнее время, тост об этом.
5. Клиент → Главная: под карточкой видно и действующее, и предложенное время и
   чей ответ ожидается. Кнопка **Отозвать запрос** доступна автору.
6. Клиент **Предложить перенос** (когда активного запроса нет) → выбрать дату и
   время → **Отправить запрос**. До подтверждения время не меняется.

Что проверяем: клиент отличает действующее время от предложенного; перенос без
ответа не меняет время; повторное действие не дублируется.

### Проведение тренировки и участники

1. Сегодня → у мини-группы 20:00 **Начать тренировку**. Открывается отдельный
   экран журнала, без подтверждения старта и автоматического посещения/списания.
2. Полоса участников: Алия 0/16, Мади «Не участвует · Отменил запись», Дана 0/12
   «Ожидает подтверждения». Деморезультаты не подставляются в сегодняшние факты.
3. У Алии нажмите **Записать**. Поля пустые; прошлый результат — отдельная подсказка.
   Введите `8,5` кг и `12` повторов. **Записать подход** подтверждает факт;
   **Повторить прошлый результат** только заполняет черновик.
4. Переключите Алия → Дана → Алия. Данные и позиция прокрутки разделены.
   У Мади ввод недоступен. Пустое поле, дробные повторы и отрицательный вес не принимаются.
5. Откройте второй подход, введите часть значения, закройте шторку. Перезагрузите
   страницу и снова откройте занятие: **Продолжить тренировку** восстановит журнал,
   а шторка подхода — неподтверждённый черновик. Проверяйте на одном и том же origin.
6. **Завершить тренировку** с пробелами открывает сводку по всей группе:
   «Сохранить записанное и завершить» / «Продолжить ввод». Пустое и черновики не
   становятся выполненными. Подтверждённое сохраняется; посещение/списание не меняются.
7. Завершённое занятие открывается через **Посмотреть результаты**, без повторного
   старта и без редактирования. Стрелка назад в незавершённом журнале просто выходит.

Хранилище: `localStorage`, отдельный ключ `trainer-prototype:journal:v1:<sessionId>`.
Это локальная проверка, не серверная синхронизация. Если другая вкладка сохранила
новую версию, устаревшая вкладка блокирует перезапись и предлагает скачать свою
копию JSON. Автоматического объединения и импорта копии пока нет.
«Сбросить прототип» возвращает на главный экран и **не удаляет** локальные журналы.
Запись без программы показывает честное пустое состояние; ввод произвольных
упражнений и назначение программы из этого экрана ещё не реализованы.

Решение по старту и визуальный план: [START-FLOW.md](../prototype/START-FLOW.md).

### Посещение и списание (идемпотентность)
1. Клиенты → Арман → любое занятие → шторка занятия.
2. **Пришёл** → шторка «Отметить посещение?» с последствием: «списать 1 занятие».
3. **Отметить и списать** → тост, движение занятий увеличивается на одну запись.
4. Повторите нажатие (через повторное открытие) — второй операции не создаётся;
   приходит предупреждение «Уже списано».

### Ошибка сохранения

Отсутствие сети не мешает локальной записи журнала. Переключатель «Нет связи»
больше не подделывает ошибку серверного сохранения в этом сценарии.
Если `localStorage` недоступно или переполнено, журнал показывает
«Только в памяти вкладки · не закрывайте её» и **Повторить сохранение**.
Завершение блокируется до успешной записи. Повреждённый журнал не перезаписывается
при открытии. Эти случаи проверяются изолированными тестами, без очистки данных браузера.

### Прочее
- **Пустой день**: объяснение и «Добавить занятие».
- **Загрузка**: скелетоны.
- **Приглашение**: переключите состояния ссылки и убедитесь, что истёкшая и
  отозванная ссылка ведут к понятному пути, а принятая — не раскрывает данные.
- **Прогресс**: при одной записи тренд не рисуется; незаписанное не равно нулю.

## Модель состояний переноса

```
pending ──accept──▶ accepted      (единственное, что меняет время занятия)
   │
   ├─decline──▶ declined          (действует прежнее время)
   ├─withdraw─▶ withdrawn         (автор отозвал)
   ├─counter──▶ counter ──accept─▶ accepted
   └─stale────▶ stale             (уведомление открывает актуальное, не повторяет)
```

Правила: запрос без ответа не меняет время; отмена записи закрывает её ожидающий
перенос; устаревшее уведомление не повторяет действие.

## Что смоделировано, а что нет

Смоделировано без бэкенда:
- локальное сохранение журнала и отдельного черновика каждого подхода;
- идемпотентность списания через ключ `charge:session:client`;
- изоляция значений по занятию и участнику, копия программы на момент старта;
- завершение без потери фактов и повторное открытие результатов для чтения.

Проверки: `node --test prototype/tests/actions.test.cjs prototype/tests/journal.test.cjs prototype/tests/reschedule.test.cjs`
— 64 теста логики, обработчиков и HTML-рендера; это не браузерный end-to-end тест. Проверка типов вспомогательного
TypeScript-проекта: `npm run typecheck` (сама статическая JS-страница им не покрыта).

23 сентября: основной цикл проверки переведён с нестабильного Computer Use
на Playwright. `npm run test:e2e` выполняет 75 браузерных проверок: пятнадцать сценариев
на desktop и ширинах 320/375/390/430. Ввод, перезагрузка, фокус, создание, участие,
перенос, встречное предложение, конфликт двух вкладок со скачиванием JSON и
reduced-motion проверяются реальным Chromium. Сквозные сценарии также проверяют
исправление подходов, возврат с сохранением прокрутки и видимость итогов после
завершения. `npm run test:e2e:typecheck`
проверяет типы новых тестов; `npm run test:e2e:report` показывает отчёт.
[Инструкция и границы покрытия](../prototype/e2e/README.md). Настоящая мобильная
клавиатура и плавность анимаций не проверены. Обычные снимки теперь используют
локальные Inter/Montserrat; отдельный тест подтверждает их загрузку без CDN.

Приглашение использует существующие GPT Image иллюстрации; состояния ссылки явно
помечены как демо, реальной авторизации нет. Повторный ввод подходов мгновенный;
редкие шторки открываются за 240 ms, прерываются вводом и учитывают reduced-motion.
Системную клавиатуру проверим в выбранном нативном стеке: она не блокирует текущую
визуальную работу. [Правила переноса дизайна](../prototype/NATIVE-DESIGN-HANDOFF.md).

### Мобильный просмотр и второй проход

При ширине окна до 600 px декоративная рамка телефона скрыта, интерфейс занимает
доступную ширину. Остаётся переключатель ролей; технические переключатели сценария
и ширины доступны на широком экране. При видимой высоте меньше 500 px панель ролей
скрывается, чтобы оставить место полям и клавиатуре. Pinch zoom не запрещён.

Шторка подхода: закреплённые имя клиента/упражнение и нижняя кнопка, прокручиваемая
середина. Enter в весе переводит к повторам, Enter в повторах явно подтверждает
подход. Кнопки ± не превращают черновик в факт. Высота учитывает VisualViewport;
реальный iOS/Android проход остаётся непроверенным.

Основание для обработки клавиатуры: [Chrome: viewport resize behavior](https://developer.chrome.com/blog/viewport-resize-behavior)
и [MDN: VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).

Переносы теперь привязаны к выбранной записи, форма принимает дату и время и
сохраняет исходную длительность. Ответить может получатель предложения, отозвать —
его автор. Встречное предложение использует новое время, повторный ответ не создаёт
повторного переноса. В интерфейсе клиента ближайшее занятие остаётся ближайшим,
запросы по другим занятиям показаны отдельно. Отмена закрывает запрос по записи;
отмена клиентом своего участия не отменяет всю группу. Перенос всей группы и запрос
на новую запись без существующего занятия пока не реализованы — ложные сообщения
об отправке убраны с доступных путей.

Расписание и переносы теперь сохраняются в `trainer-prototype:appointments:v1`.
Создание занятия реально добавляет запись со статусом ожидания согласия, проверяет
будущее время, длительность, клиентов, программу и пересечения. Клиент может
подтвердить участие. Отмена и история встречных предложений переживают перезагрузку.
Ошибка записи не изменяет исходное расписание и не показывается как успех.
Повреждённое сохранение не перезаписывается; устаревшая вкладка получает предупреждение.

Посещение, списание, оплаты и балансы пока живут в памяти демо-сеанса и сбрасываются
при перезагрузке. Новые карточки клиентов сохраняются со снимком расписания при его
успешном изменении. Серверной синхронизации, доставки уведомлений и транзакций нет.
Проверки ролей в этом JS-прототипе не заменяют серверную авторизацию.

Computer Use возвращал `noWindowsAvailable` и invalid element ID; переподключение
не устранило сбой. Поэтому автоматизация использует отдельный Chromium Playwright
и новый контекст на каждый тест. Личный браузер и локальные данные пользователя
не используются и не очищаются.

Открытие шторки посещения больше не отмечает присутствие до выбора действия.
«Только отметить» не создаёт списание; «Отметить и списать» идемпотентно. Исправление
посещения не отменяет ранее созданную операцию списания автоматически.

История клиента теперь включает мини-группы и различает посещение, неявку, отмену,
завершённый журнал и запись без отметки. Календарь посещений строится из отметок,
а не из расписания. Списание относится к пакету выбранного клиента; остаток
уменьшается один раз. При отсутствии доступного пакета прототип предлагает только
отметить присутствие, не списывая из чужой покупки.

Журнал сохраняет копию даты/времени на момент старта наряду с программой: завершённые
результаты не получают другое время при сбросе демонстрационного расписания.

Не реализовано намеренно (отложено в handoff v2 §10): приём платежей, push,
QR, чат, автоматические штрафы, офлайн-синхронизация, роли клуба. Плюс
возможность редактировать результаты клиентом — открытый вопрос.

## Где менять UI/UX

- Токены: `prototype/css/tokens.css`.
- Повторяемые компоненты: `prototype/css/components.css`.
- Разметка экрана: `prototype/js/screens/*.js`.
- Шторки и их копирайт: `prototype/js/sheets.js`.
- Логика и состояния: `prototype/js/store.js`.
- Данные: `prototype/js/data.js`.

Порядок подключения скриптов в `index.html` важен: `icons → data → session-repository → store → ui →
sheets → screens → app`.

### Calendar update

Week arrows navigate across months; Today returns to the demo date. Counts exclude cancelled appointments. Appointment rows open details; pending transfer links open requests. The add button preserves the selected date, and free windows also prefill time and duration. Overlap groups are calculated from actual intervals.

### Updated Clients page

Search matches names (case-insensitive) and formatted phone numbers. All / To pay / No booking filters combine with search. Upcoming sessions are derived from the schedule, excluding cancelled bookings and cancelled group participation. The add button opens a name-only creation sheet; a new card appears in the in-memory roster and can be opened before client registration. New cards last until page reload, like other prototype data. Empty, no-results, loading, and offline states are available.

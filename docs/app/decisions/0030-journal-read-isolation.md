# 0030. Изоляция серверного журнала и заметок

- **Статус:** Принято для схемы; синхронизация остаётся отдельной задачей
- **Дата:** 01.10.2026
- **Задача:** SOM-28

## Контекст

Журнал требует стабильных ID для офлайн-записей, снимков планов и изоляции
участников группы. Временные правила OPEN-QUESTIONS №6 и №8 разрешают клиенту
читать только завершённый собственный журнал; результаты вводит тренер.
Личная заметка тренера не должна попадать клиенту вместе с остальными данными.

## Решение

workout_instances связывает запись занятия с клиентом и необязательной личной
программой. Состав журнала хранится в workout_exercises, результаты — в
set_results. Внешние ключи включают workspace; связь с программой и booking
проверяет также клиента. Источник замены упражнения принадлежит тому же журналу.
ID журнала и его строк задаёт устройство, вес хранится целым числом граммов,
пустое значение отличается от нуля. Серверные записи имеют revision и аудит.

Журнал допускает добавленное на месте упражнение без исходного плана: ноль
плановых подходов и пустые плановые значения. При замене старая строка и её
результаты сохраняются, строка помечается пропущенной, новая ссылается на неё.
Ограничение библиотеки в 50 строк не переносится на историю замен журнала.

session_notes содержит только открытые заметки, private_notes — личные заметки
к занятию или карточке клиента. Это разные таблицы с разными политиками.
Не добавляется второй переключатель shared внутри публичной заметки: будущая
команда изменения видимости должна атомарно работать с обеими таблицами.

Владелец читает данные своего workspace. Клиент читает свой workout_instance
только при заполненном finished_at и связанные с ним упражнения, подходы и
открытые заметки. Совпадение group_session_id не даёт доступа к чужим данным.
private_notes и sync_operations доступны только владельцу: результат операции
может содержать приватный текст. Включение RLS и закрытие прямой записи входят
в ту же миграцию, что создаёт таблицы.

## Границы

Таблица sync_operations задаёт место хранения результата операции, но сама по
себе не реализует повторы, конфликты или синхронизацию. apply_operations,
локальная SQLite outbox и проверка двух устройств относятся к SOM-29.
Схема не подключает существующий демонстрационный журнал к серверу.
Решения владельца о конфликтах и доступе к черновикам остаются открытыми.

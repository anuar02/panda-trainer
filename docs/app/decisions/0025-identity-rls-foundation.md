# 0025. Базовая схема идентичности и границы записи

- **Статус:** Принято
- **Дата:** 01.10.2026
- **Задача:** SOM-18

## Контекст

DATA-MODEL определяет profiles, trainer_workspaces, client_records и invitations.
Карточка клиента существует до регистрации. Прямая запись user_id или владельца
пространства дала бы обход будущего процесса приглашения и границ арендатора.
Выбор провайдеров входа ещё не принят; создание этой схемы его не требует.

## Решение

Четыре таблицы включают RLS, audit-поля и revision. Собственный профиль доступен
пользователю; пространство доступно владельцу; карточки читает владелец либо
связанный клиент, меняет только владелец. Один владелец имеет одно пространство.
Функции is_workspace_owner и my_client_record_ids — stable security definer с
фиксированным search_path и явным auth.uid(). PUBLIC/anon не могут их вызывать.

Column grants ограничивают прямую запись безопасными пользовательскими полями.
Идентификаторы, owner_user_id, workspace_id, user_id, audit-поля и revision нельзя
подменить UPDATE-запросом. user_id карточки нельзя задать и при INSERT. Триггер
обновляет updated_at и revision. Это метаданные версии; атомарная проверка
base_revision будет добавляться вместе с соответствующими командами/RPC.

Приглашения пока доступны владельцу только как безопасные метаданные: token_hash
не выдаётся Data API, INSERT/UPDATE/DELETE закрыты authenticated. Создание и
принятие приглашения будут отдельной задачей SOM-21. Эта миграция не предоставляет
фиктивно работающий invite flow и не связывает экранные демо с сервером.

Seed содержит только вымышленные имена прототипа, два пространства для проверки
изоляции, связанные и несвязанные карточки. Телефоны null, email используют
example.test, паролей и провайдеров входа нет. Seed не создаёт действующую ссылку
приглашения. Для тестов используется отдельный локальный стек, не облачный проект.

Типы генерируются из public локальной БД закреплённым Supabase CLI; TypeScript
printer удаляет сгенерированные комментарии согласно CONVENTIONS, Prettier
нормализует формат. CI сравнивает результат с database.types.ts и падает при
расхождении. Типы описывают SQL-структуру, а не заменяют проверку grants/RLS.

## Последствия

Пользователь не может напрямую привязать клиентскую карточку, принять приглашение
или передать пространство. Эти ограничения должны сохраняться в следующих RPC.
created_by допускает null для системных операций postgres без JWT; Data API
использует auth.uid() по умолчанию и не имеет права подменять автора.
Физические удаления не разрешены authenticated; архивирование карточки — поле.

Проверки: supabase/tests/database/foundation.test.sql и rls_guard.test.sql;
команды воспроизведения — supabase/README.md. Production auth, принятие invite,
проверка на двух авторизованных телефонах и облачная публикация не входят в этот
локальный foundation. Статус этапа не закрывается этой миграцией.

# 0027. Серверное создание занятия и сериализация пересечений

- **Статус:** Принято
- **Дата:** 01.10.2026
- **Задача:** SOM-25

## Контекст

Локальное расписание (ADR 0018) допускает персональные занятия с пересечением
после явного подтверждения тренера. Проверка только в приложении позволила бы
двум параллельным запросам одновременно увидеть свободный интервал.

## Решение

Миграция создаёт group_sessions, bookings и schedule_proposals. Один участник —
одна booking; мини-группа объединяет несколько bookings общим временем начала
и окончания при создании. Составные внешние ключи не допускают чужой workspace
в связи с клиентом, группой или предложением. Статус новой booking — proposed;
подтверждение клиентом и последующие переходы будут командами SOM-27.

create_booking_set определяет workspace по auth.uid(), не по входному workspace ID.
Только владелец может создать занятие для активных карточек своего пространства.
RPC блокирует строку workspace до проверки пересечений и записи. Все будущие
команды изменения расписания должны применять тот же порядок блокировок:
workspace, затем booking/предложение. Это обязательный контракт для SOM-27.

Интервал пересекается при start < other_end AND end > other_start. Касание концов
не считается пересечением. Предложенные и подтверждённые bookings занимают время;
отменённые не занимают. Участники одной группы сворачиваются в одно предупреждение.
При конфликте без collision_ack RPC возвращает requires_overlap_ack и список
конфликтов, не создавая строк. Подтверждённый тренером повтор проверяет текущие
пересечения под той же блокировкой и создаёт занятие атомарно.

Моменты хранятся timestamptz; граница суток вычисляется по IANA-зоне workspace
(по умолчанию Asia/Almaty), без фиксированного UTC-смещения. Начало в будущем,
конец позже начала и не позже следующей местной полуночи. Ровно полночь допустима,
как end=1440 в локальном домене.

request_id принадлежит workspace. Успешный запрос сохраняет нормализованный
payload на первой booking и при повторе возвращает те же booking IDs. Изменённый
payload с тем же ключом отклоняется. Проверка receipt предшествует проверкам
текущего времени/архива клиента, чтобы повтор уже успешной операции не стал
ошибкой. Время в payload не зависит от TimeZone SQL-сессии. Предварительное
предупреждение без записи не занимает ключ — тренер может подтвердить тот же запрос.

RLS: тренер читает своё расписание, клиент — только свои bookings и связанные
предложения/общие времена группы. Внутренние request_id/request_payload не входят
в SELECT grants: receipt группы не раскрывает клиенту ID других участников.
Прямые INSERT/UPDATE/DELETE всех трёх таблиц закрыты; запись только через команды.

## Границы и проверки

Это основа создания с выбором программы позже. Программы/снимки, переносы, отмены,
подтверждение участником, клиентский transport и визуальная приёмка ещё открыты.
Наличие schedule_proposals не означает работающий сценарий переноса.

pgTAP проверяет права, группы, пересечения, явное подтверждение и повтор запросов.
supabase/tests/schedule_concurrency.py открывает две реальные SQL-сессии: вторая
ожидает блокировку первой, затем получает предупреждение либо те же IDs для
одинакового request_id. Конкурентный тест включён в database CI job.
Результаты и воспроизведение — supabase/README.md. Облачная публикация и два
авторизованных телефона не проверены этим пакетом.

# 0075. Валидация и фиксированная сессия чтения расписания

- **Статус:** Реализовано технически; runtime и приёмка открыты
- **Дата:** 03.10.2026
- **Задача:** SOM-26

## Контекст

Today, неделя и создание уже читают production расписание. Несколько запросов
одного snapshot использовали изменяемую сессию общего Supabase client, а hook
различал только пользователя и workspace. SDK-типы не проверяют ответы в runtime;
неограниченная пагинация и malformed связанные строки могли дать неверные окна.

## Решение

Чтение подписывается на существующий auth event контракт и проверяет getSession
до и после каждого запроса, а также перед возвратом. JWT `session_id` и `sub`
используются как идентификатор входа, не как самостоятельное доказательство
авторизации. Авторизацию выполняет Supabase/RLS. Если идентификатор входа
неизвестен или actor не совпадает с ожидаемым, чтение закрывается ошибкой.
Workspace возвращается только с совпавшим owner_user_id и запрошенным id.

Все PostgREST запросы и proposal RPC получают один исходный Authorization header.
Credentials существуют только внутри живого fence; результат, ошибки и ключи
hook не содержат access token. Refresh с тем же actor/session_id разрешён,
исходный token не заменяется. SIGNED_IN/SIGNED_OUT и прочие изменения auth
инвалидируют чтение даже при том же аккаунте; новый session_id обнаруживается
и без события. Неуспешный запрос с истёкшим исходным token требует нового чтения.
Auth provider и account export не изменяются.

Runtime validators проверяют выбранные поля каждой таблицы: канонические lowercase UUID/scope,
положительные int4 ревизии, известные статусы, реальные UTC даты
(Z или +00:00), упорядоченные интервалы, timezone и availability. Для рабочих
часов требуется точность до минуты, поскольку agenda работает в минутах;
ненулевые секунды не округляются в свободные окна. Сохраняется SQL-набор
usual_session_minutes 45/60/90. Дубликаты, лишние/missing связанные строки,
неверный proposal base_revision и несколько pending proposals одного booking
отклоняются. Отсутствующая необязательная программа остаётся допустимой.

Bookings и all-time proposals читаются по 500 строк, максимум 20 страниц на
коллекцию. Если последняя разрешённая страница полная, возвращается readLimit,
даже при ровно 10000 строках: доказать полноту в разрешённом бюджете нельзя.
Связанные booking/client/program строки запрашиваются batch по 200 ID с
проверкой каждого ответа. Предложения вне недели сохраняются с их booking.
Никакого успешного частичного snapshot нет.

Hook использует существующий typed WorkspaceSchedule seam и локальный controller
поколений. Новая сессия, auth loading/failure, новый workspace/week, retry, blur
и unmount скрывают или отбрасывают предыдущий snapshot. Today/week/create
сохраняют свои read API и существующие команды; новые экраны не создаются.

## Альтернативы

- Только проверки getSession без фиксированного header: другой actor мог бы
  авторизовать промежуточный запрос изменяемого client.
- Сравнение только user_id: новый вход того же аккаунта не отличался бы.
- Сравнение access_token как идентификатора входа: refresh и новый login
  не различались бы. Нужен стабильный session_id и auth events.
- Ограничение с успешным обрезанием: теряются bookings/proposals и появляются
  ложные свободные окна.

## Проверка и ограничения

Synthetic service/session/controller/hook тесты и полный app check описаны в
[отчёте](../../../app/review/som-26-schedule-read-fencing/README.md).
Это session fencing, а не транзакционный snapshot всех таблиц: конкурентные
изменения данных могут потребовать retry. SQL/RLS/live API, native/parity,
два устройства и принятие экранов владельцем здесь не проверены.

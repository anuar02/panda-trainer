# 0003. Офлайн только для журнала: SQLite + очередь операций

- **Статус:** Предложено (подтвердить до начала этапа 5)
- **Дата:** 29.09.2026
- **Кто решил:** исполнитель, по требованиям `prototype-fresh/SYNC-DESIGN.md`

## Контекст

В зале часто нет сети. Потерянный подход — худшая ошибка продукта. При этом полный
офлайн для всего приложения (`trainer-crm-agent-plan.md` §7) отложен.

## Решение

- Офлайн-первым делаем **только журнал тренировки**. Остальные экраны — онлайн с кэшем
  TanStack Query (чтение последних данных, запись требует сети).
- Локальное хранилище — `expo-sqlite`: предзагруженные занятия, программы, прошлые
  подходы и таблица `outbox`.
- Каждое изменение журнала — операция `{operation_id, kind, entity_id, base_revision,
  device_id, payload, created_at}`; запись в локальные таблицы и `outbox` одной транзакцией.
- Отправка пачкой через RPC `apply_operations`. Сервер хранит `operation_id` в
  `sync_operations`: повтор возвращает прежний результат, второй подход не создаётся.
- Устаревшая `base_revision` → ответ `conflict` с серверной версией; телефон хранит
  обе и показывает тренеру выбор. Автоматического «последний победил» нет.
- Интерфейс различает «Сохранено на телефоне» и «Синхронизировано».

## Рассмотренные варианты

- **PowerSync / ElectricSQL** — готовая синхронизация Postgres ↔ SQLite, но платный
  сервис и ещё один поставщик; можно пересмотреть, если своя очередь окажется дорогой.
- **WatermelonDB** — зрелая, но своя модель синхронизации и last-write-wins по полям.
- **Только кэш TanStack Query** — нет гарантии сохранения записи при закрытии приложения.

## Последствия

- Журнал — самая сложная часть; на неё заложен этап XL.
- Нужны тесты очереди: повтор, дубликат, порядок, конфликт, закрытие приложения.
- Политика конфликтов окончательно подтверждается владельцем ([OPEN-QUESTIONS](../OPEN-QUESTIONS.md) №3).

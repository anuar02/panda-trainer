# 0033. Атомарная настройка тренера

- **Статус:** Принято; экран и native-приёмка отдельно
- **Дата:** 01.10.2026
- **Задача:** SOM-20

## Решение

`complete_trainer_onboarding` создаёт профиль, пространство, настройки рабочего
времени, стартовый каталог и необязательную карточку первого клиента одной
транзакцией. SECURITY INVOKER сохраняет действующие RLS и column grants;
идентификатор пользователя берётся только из `auth.uid()`.

Транзакционная advisory-блокировка по пользователю сериализует два устройства.
Повтор возвращает существующее пространство, не меняет профиль/настройки и не
создаёт второго клиента. Ошибка поздней вставки откатывает всю настройку.
RPC не предназначена для редактирования существующего профиля.

Поля берутся из `prototype-fresh/js/screens/welcome.js`: специализации, дни
недели (понедельник = 0), начало/конец дня, обычная длительность 45/60/90 минут,
необязательные имя/телефон клиента. Название пространства внутри базы совпадает
с именем тренера: прототип не требует отдельного поля. Специализации хранятся
как коды, независимо от русского текста. Повторяющиеся дни/коды нормализуются.
Рабочее время — предпочтение для будущего подбора окон, не запрет записи вне него.

Имя тренера и клиента ограничены 120 символами, телефон — 80. Пустой телефон
сохраняется как NULL; телефон без имени клиента отклоняется. Клиент остаётся
непривязанным (`user_id IS NULL`), пока отдельное приглашение не принято.
Домен приглашений pending: настройка не создаёт ссылку и не отправляет сообщения.

## Создание следующих клиентов

`create_client_record(client_name, client_phone, request_id)` проверяет владельца
пространства и создаёт непривязанную карточку. Приватный receipt связывает
workspace, actor и request_id с нормализованным запросом и исходным результатом.
Повтор после сетевой ошибки возвращает тот же ID даже после правки карточки;
другой payload с тем же ключом отклоняется. Блокировка workspace сериализует
создание, receipt не доступен клиентам. UI сохраняет request_id при повторе
неудачного запроса с тем же именем.

## Границы экрана

Сохраняется пятишаговый сценарий прототипа. В реальном аккаунте имя не заполняется
вымышленным именем тренера из DB; пропуск требует реального непустого имени.
Сообщение «ссылка готова» не показывается без настоящего приглашения. Эти отличия
фиксируют реальные ограничения, а не меняют выбранный дизайн.
Демо-маршруты не используются как рабочее пространство вошедшего пользователя.

## Проверка

pgTAP проверяет доступ, валидацию, сохранение прежних значений, каталог, отсутствие
повторного клиента и откат. `supabase/tests/onboarding_concurrency.py` проверяет
две реальные SQL-сессии. Точные результаты и UI-приёмка — в ROADMAP и отчёте
экрана; наличие RPC само по себе не закрывает SOM-20.

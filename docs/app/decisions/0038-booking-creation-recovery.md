# 0038. Восстановление команды создания занятия

- **Статус:** Принято технически; подключение UI открыто
- **Дата:** 02.10.2026
- **Задача:** SOM-26

Команда создания использует существующий RPC `create_booking_set` из ADR 0027.
Транспорт фиксирует участников, UTC-интервал, подтверждение пересечения и request
ID при создании операции. Одновременные вызовы используют один Promise;
успешный ответ сохраняется, после ошибки повторяется тот же payload и request ID.
Перед отправкой проверяется текущий аккаунт, его токен закрепляется в RPC.
UUID нормализуются без учёта регистра.

Ответ проверяется до передачи потребителю: число bookings соответствует числу
участников, группа присутствует только для нескольких участников, предупреждение
не содержит созданных записей. Пересечения возвращаются в каноническом UTC.
Предупреждение не считается успехом и не включает подтверждение автоматически.

`workspace-scheduling/pending.ts` хранит одну неопределённую команду на аккаунт и
workspace в AsyncStorage. Перед отправкой потребитель обязан сохранить команду;
после рестарта — восстановить и повторить её. Другой payload не перезаписывает
ожидающий результат. Повреждённые данные блокируют чтение, замену и удаление.
Записи сериализуются, удаление проверяет request ID. В хранилище нет токена сессии.

Полученное предупреждение означает, что записей не создано: потребитель может
снять ожидающую команду и после явного согласия создать новую с подтверждением.
При потере ответа менять подтверждение или request ID нельзя.

Альтернатива — держать request ID только в памяти — теряет возможность безопасного
повтора после рестарта. Общая SQLite outbox журнала здесь не требуется: это
отдельная серверная команда расписания, а не офлайн-запись подходов.

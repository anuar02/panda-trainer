# 0037. Чтение серверного расписания и границы недели

- **Статус:** Принято технически; UI-интеграция и приёмка открыты
- **Дата:** 01.10.2026
- **Задача:** SOM-26

## Контекст

Серверная основа расписания хранит занятия, группы и предложения в UTC. Рабочая
неделя и часы тренера уже заданы в workspace (`working_days`, `day_start`,
`day_end`, `usual_session_minutes`, `timezone`). Списки могут быть длиннее
ограничения одной страницы PostgREST, а предложения на перенос нужно учитывать,
даже если исходное занятие находится за пределами отображаемой недели.

## Решение

Транспорт чтения остаётся отдельным от демо-расписания. `loadWorkspaceSchedule`
в `app/src/features/workspace-scheduling/service.ts` принимает UUID workspace и
канонические UTC ISO-границы с `Z`, проверяет порядок и ограничивает интервал 42
днями. Запрос занятий использует условие пересечения полуоткрытых интервалов:
`starts_at < endsAtUtc` и `ends_at > startsAtUtc`. Он сохраняет все серверные
статусы и идентификаторы групп. Данные читаются с детерминированной сортировкой
и страницами по 500 строк; связанные записи запрашиваются пакетами не более 200
UUID.

Результат включает только поля доступности workspace, занятия с именем клиента и
все ожидающие предложения. Предложение возвращается вместе с исходным занятием
и именем клиента, даже если это занятие вне запрошенного интервала. Имена
считываются и для архивных карточек, связанных с существующими занятиями.
Внутренние идентификаторы пользователей, телефоны и поля идемпотентности не
передаются потребителю. Для определения направления предложения сервис сравнивает
`author_user_id` с `owner_user_id` workspace и отдаёт только
`authorRole: 'trainer' | 'client'`.

`app/src/features/workspace-scheduling/clock.ts` использует
`Intl.DateTimeFormat` с IANA-зоной workspace для `workspaceDateKey(value,
timeZone)`, `workspaceMinuteOfDay(value, timeZone)` и
`workspaceMondayWeekday(value, timeZone)`. `calendarWeekDateKeys(dateKey)` строит
семь ключей недели с понедельника. Смещение UTC не фиксируется вручную.
`paddedUtcWeekBounds(dateKey)` возвращает UTC-границы от понедельника выбранной
календарной недели минус одни сутки до следующего понедельника плюс одни сутки.
Этот запас покрывает сдвиг между локальной неделей и UTC; вызывающая сторона
обязана затем оставить только даты нужной недели в зоне workspace.

## Рассмотренные варианты

- Запрашивать отдельный UTC-интервал для каждого локального дня — сложнее
  объединять непрерывные события и корректно учитывать зоны с переходом времени.
- Не ограничивать диапазон и читать одним запросом — ответ может быть молча
  усечён лимитом PostgREST.
- Ограничивать ожидающие предложения тем же интервалом, что и занятия — скрывает
  входящий запрос, если исходное занятие назначено вне видимой недели.
- Передавать авторский UUID в UI — это не требуется для счётчиков и раскрывает
  идентификатор аккаунта; используется производная роль автора.

## Последствия

Читатель может строить локальные дневные и недельные представления без потери
данных из-за пагинации и без утечки полей карточки клиента. Интервал чтения
ограничен 42 днями; UI должен использовать workspace timezone и точно фильтровать
выбранные локальные даты после чтения расширенной UTC-недели. Этот пакет не
подключает экран расписания и не объявляет визуальную или нативную приёмку
завершённой.

Unit-тесты `app/tests/workspace-scheduling-clock.test.ts` и
`app/tests/workspace-scheduling.test.ts` покрывают преобразования времени,
границы интервала, пагинацию, связанные архивные карточки, направления
предложений и обработку ошибок.

Проверки: 13 focused tests; общий `npm run check` — 435 тестов / 59 suites,
TypeScript, ESLint и Prettier проходят. Expo export всех платформ проходит.

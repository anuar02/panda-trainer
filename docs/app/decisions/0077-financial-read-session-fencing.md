# 0077. Изоляция финансовых чтений по auth-сессии

- Статус: реализовано технически; live auth и приёмка владельца открыты
- Дата: 03.10.2026
- Задача: SOM-34

## Контекст

На проверенной базе `96db40a` billing/payments фиксировали bearer после одного
getSession. Hooks различали actor/workspace/client/attempt, но не повторный вход
того же пользователя. В этой базе auth provider не предоставляет отдельной
идентичности сессии; account-export по ADR 0074 сравнивает access token и
останавливается при refresh. Указанный в брифе отдельный влитый контракт
идентичности auth в доступном коде отсутствует. Эти системы остаются неизменными. Перед публикацией база обновлена до `90b7f73`:
SOM-26 ввёл локальный JWT session_id контракт расписания (ADR 0075), SOM-35 —
контракт клиентской истории (ADR 0076). Финансовый helper сохраняет ту же
семантику стабильного JWT session_id / sub и fail-closed decoding, оставаясь
внутри границ этих features; запрещённые модули не импортируются и не меняются.

## Решение

Локальный read helper в trainer-billing извлекает пару user ID / JWT session_id.
Это маркер жизненного цикла, не проверка подлинности JWT: авторизацию выполняет
Supabase с исходным bearer. Нет session_id, неверный sub или malformed token —
ошибка unavailable; fallback на user ID, access/refresh token отсутствует.
TOKEN_REFRESHED с тем же session_id не создаёт новую сессию. SIGNED_OUT всегда
инвалидирует чтение, включая немедленный повторный вход того же user.

Подписка устанавливается до первоначального getSession и снимается в finally.
Каждая страница проходит getSession до запроса и после ответа; итоговый результат
проверяется снова после runtime/relation validation. Все запросы одного чтения,
включая вспомогательные покупки для payments, используют один захваченный bearer
и скопированный expected actor/workspace/client. При refresh старый bearer может
дать серверную ошибку; автоматической смены авторизации посреди чтения нет.

Hooks имеют отдельную подписку на lifecycle и локальную epoch, изменяемую
синхронно в callback. Epoch входит в key и проверяется вместе с active/key перед
success/error. Старый retry не запускает новый запрос после смены scope/session
или unmount. Refresh той же сессии сохраняет snapshot и не перезапускает чтение.
Нет общего auth refactor, изменений provider, mutation API, UI или SQL.

Каждая таблица читается страницами по 500, максимум 10 000 строк. Exact count
обязателен, стабилен между страницами и определяет ожидаемую длину каждой
страницы. Превышение лимита, отсутствующий count, усечённая/лишняя страница,
дубликаты ID (без учёта регистра) или изменение count — ошибка request,
никогда truncated success. Пустой snapshot разрешён только при count = 0.

Billing проверяет scoped связи revisions/attendance, credits/purchases/attendance,
restore/original, уникальность списания и grant, полный grant и допустимый остаток.
Payments дополнительно читает bounded purchases под той же авторизацией и
использует существующую domain projection для scoped связей, reversal integrity
и capped totals. Canonical integer money strings и поведение ADR 0059 сохраняются.

## Ограничения

Раздельные PostgREST-чтения не являются одной транзакцией БД. Конкурентные записи
могут вызвать безопасную ошибку и потребовать повторного чтения; неизменный count
сам по себе не доказывает неизменность содержимого. Exact count и дополнительное
чтение покупок увеличивают стоимость запросов. Лимит не является продуктовым
ограничением количества данных: при превышении нужен будущий серверный snapshot
контракт, а текущий read отказывает. Live JWT/session_id, refresh, SQL/RLS и native
поведение проверяются отдельно; synthetic tests не заменяют эти проверки.

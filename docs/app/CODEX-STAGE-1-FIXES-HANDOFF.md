### PR A — исправления каркаса (`fix/foundation-review`)

**A1. Шторка вызывает `onClose` дважды** — `app/src/ui/sheet.tsx`.
Сейчас: кнопка «Закрыть» или системная «Назад» → `onClose()` → родитель ставит
`open=false` → эффект вызывает `dismiss()` → `onDismiss` → `handleDismiss` → `onClose()`
второй раз. Сегодня безвредно (`setOpen(false)` идемпотентен), но сломает шторки с
побочным эффектом при закрытии (сброс черновика подхода, сохранение).

Нужно: `onClose` вызывается ровно один раз на одно закрытие, кто бы его ни начал.
Вариант: в `handleDismiss` звать `onClose` только если закрытие начал не родитель
(жест, фон). Закрытие, начатое пропом `open=false`, `onClose` не вызывает — родитель уже
знает. Кнопка «Закрыть» и BackHandler могут вызывать `ref.current?.dismiss()` и
полагаться на `onDismiss`, а не на прямой `onClose`.
Сохранить защиту из ADR 0006 (нет `dismiss()` до первого `present()` и повторного после
жеста, upstream gorhom #2669).

Тесты в `app/tests/sheet.test.tsx`:
- Первый тест сейчас закрепляет двойной вызов — переписать.
- Закрытие кнопкой → `onClose` 1 раз.
- Закрытие жестом (`mockOnDismiss`) → `onClose` 1 раз.
- Закрытие пропом `open=false` → `onClose` 0 раз.
- Системная «Назад» на Android → `onClose` 1 раз (замокать `BackHandler`).
- Повторное открытие после каждого варианта работает.
Проверить на эмуляторе Android: кнопка, жест, «Назад», повторное открытие.

**A2. Удалить `app/LICENSE`.** Это MIT-лицензия шаблона Expo («650 Industries»), она
неверно описывает права на продукт. Лицензию проекта не выбирать — если нужна,

**A3. Тема пересоздаёт контекст на каждый рендер** — `app/src/ui/theme.tsx`.

### PR C — этап 2, часть без выбора способа входа (`feat/stage-2-schema`)

**Блокер:** ADR 0004 (вход) в статусе «Предложено, подтвердить до начала этапа 2».
Экраны входа, Apple/Google, настройку SMTP и `expo-secure-store` **не начинать** до
подтверждения владельцем. Добавить в `OPEN-QUESTIONS.md` вопрос №10: «Подтвердить
ADR 0004: e-mail OTP + Apple + Google; домен для ссылок приглашений» с крайним сроком
«до экранов входа этапа 2». В PR B или C явно попросить владельца ответить.

Не зависит от способа входа, можно делать сразу — по `docs/app/DATA-MODEL.md`:

1. Миграция: `profiles`, `trainer_workspaces`, `client_records`, `invitations`.
   RLS включён в той же миграции. Функции `is_workspace_owner`,
   `my_client_record_ids` — `security definer`, `set search_path = ''`.
2. `invitations`: хранится только хэш токена, срок действия, одноразовость. RPC
   `accept_invitation(token text)` — проверяет срок, одноразовость и что вызывающий
   ещё не привязан к другой карточке этого пространства; повторный вызов с тем же
   токеном безопасен.
3. pgTAP (`supabase/tests/database/`): тренер A не видит клиентов тренера B; клиент видит
   только свою карточку; подбор ID не открывает чужие данные; просроченное и
   использованное приглашение отклоняется; guard RLS из этапа 1 продолжает проходить.
   Пользователей в тестах создавать через `auth.users` и `set local role authenticated` +
   `request.jwt.claims` — не зависит от способа входа.
4. `supabase gen types typescript --local` → `app/src/lib/database.types.ts`; в CI —
   шаг, который падает, если сгенерированный файл отличается от закоммиченного.
5. `supabase/seed.sql`: вымышленные тренеры и клиенты по `prototype-fresh/js/data.js`,
   без реальных людей.
6. `DATA-MODEL.md` — сверить с тем, что получилось; расхождения описать.
7. Клиент Supabase в `app/src/lib/supabase.ts` (только `EXPO_PUBLIC_*`) — можно
   подключить, но без хранения сессии, пока ADR 0004 не подтверждён.

**Готово, когда (часть C):** все pgTAP-тесты прав зелёные локально и в CI, типы
сгенерированы и проверяются. Экраны этапа 2 — после ответа по ADR 0004.

# Архитектура приложения

Статус: технический каркас реализован (29.09.2026), локальная база проверена
(db lint, pgTAP 1/1; CI PR #17 зелёный). Паритет с прототипом и нативная приёмка
остаются открытыми; этап 1 не принят до PR D и одобрения снимков.
Работают Expo Router, NativeWind, тема, шрифты, i18next и общие UI-компоненты.
Остальные библиотеки, потоки данных и предметные модули ниже — план следующих этапов;
они пока не подключены. Подробности: `app/README.md`, ADR 0006.
Временный выбор роли — только навигация, без авторизации и серверных прав.

## Общая схема

```
Телефон (Expo, React Native)                     Supabase
┌───────────────────────────────┐               ┌──────────────────────────────┐
│ Экраны (Expo Router)          │               │ Auth: e-mail OTP, Apple,     │
│   ↓ хуки                      │               │       Google                 │
│ Серверное состояние           │  HTTPS / WSS  │ Postgres                     │
│   TanStack Query ─────────────┼──────────────▶│   таблицы + RLS              │
│ Журнал тренировки             │               │   RPC: переносы, списания,   │
│   expo-sqlite + очередь ──────┼──────────────▶│        apply_operations      │
│ Состояние интерфейса          │               │ Realtime: уведомления        │
│   Zustand (мало)              │◀──────────────┤ Storage: пока не нужен       │
└───────────────────────────────┘               └──────────────────────────────┘
```

- Чтение: через `supabase-js`, права ограничивает RLS.
- Простые записи (карточка клиента, упражнение, шаблон): прямые `insert/update` под RLS.
- Записи с бизнес-правилами (перенос, посещение, списание, оплата, подходы журнала):
  только через RPC-функции Postgres. Прямая запись в эти таблицы закрыта.
- Edge Functions — только если понадобится секрет или внешний сервис; на старте их нет.

    (trainer)/               вкладки тренера

  src/
    features/<модуль>/       экраны-компоненты, хуки, запросы, схемы одного модуля
    domain/                  чистые функции без React и сети (пересечения, статусы,
                             форматирование весов и денег)
    offline/                 expo-sqlite, очередь операций, синхронизация журнала
    ui/                      общие компоненты и тема
    lib/                     клиент Supabase, database.types.ts, i18n
  assets/                    шрифты, маскот
  review/                    снимки экранов для приёмки
supabase/
  migrations/                SQL-миграции, только вперёд
  tests/                     pgTAP: права и бизнес-правила

Модули `features/` повторяют предметные области из `trainer-crm-agent-plan.md`:
`identity`, `clients`, `library`, `scheduling`, `workouts`, `billing`, `progress`,
`notifications`, `mascot`. Модуль не импортирует внутренности другого модуля, только
его публичный `index.ts`.

## Потоки данных

### Обычный экран (онлайн с кэшем)

Экран → хук `useClients()` → TanStack Query → `supabase.from('client_records')`.
Кэш сохраняется на устройстве, поэтому при плохой сети показываются последние данные
с пометкой времени. Без сети запись на таких экранах недоступна и это видно.

### Журнал тренировки (офлайн-первый)

Подробно — [ADR 0003](decisions/0003-offline-sync.md).

1. При открытии «Сегодня» с сетью: занятия на сегодня и завтра, их программы и
   прошлые подходы участников сохраняются в SQLite.
2. Запись подхода: пишется в SQLite и в очередь `outbox` одной транзакцией. Экран
   сразу показывает «Сохранено на телефоне».
3. Отправитель очереди при наличии сети вызывает RPC `apply_operations` пачкой.
   Сервер применяет каждую операцию один раз (`operation_id` — первичный ключ
   журнала операций) и возвращает ревизии.
4. Подтверждённые операции удаляются из очереди, статус — «Синхронизировано».
5. Конфликт (изменённая на другом устройстве ревизия) не перезаписывает данные: он
   сохраняется и показывается тренеру для выбора.

### Деньги и списания

Только RPC: `mark_attended`, `undo_attendance`, `add_payment`, `link_attendance_to_purchase`.
Каждая функция проверяет владельца, блокирует строку пакета (`for update`) и принимает
ключ идемпотентности. Клиентский код не вычисляет остаток — он читает представление
`client_balances`.

## Окружения

| Окружение | Supabase | Данные | Кто пользуется |
| --- | --- | --- | --- |
| local | `supabase start` (Docker) | `seed.sql` | разработчик, CI |
| dev | облачный проект, Free | вымышленные | тестовые сборки |
| pilot | облачный проект в согласованном регионе | реальные | после этапа 10 |

Ключи: в приложении только URL и anon key (`EXPO_PUBLIC_*`). Service role key —
только в секретах CI и никогда в `app/`.

## Безопасность

- Все таблицы с `enable row level security`; политика по умолчанию — запрет.
- Личные заметки тренера — отдельная таблица без политики чтения для клиента.
- Токен приглашения хранится хэшем; принятие — RPC с проверкой срока и одноразовости.
- Сессия хранится в `expo-secure-store`.
- Переключатель роли в приложении — только навигация; права определяет база.

# Синхронизация: варианты для решения владельцем продукта

28 сентября 2026. Статус: проект для обсуждения, **реализации нет**.
Не выбраны поставщик, регион, бюджет, способ входа и политика конфликтов.

## Что хранится сейчас

Инвентаризация: `graft grep localStorage`, `js/session-repository.js`, `js/store.js`,
`js/visual.js`. Ниже все ключи приложения; тестовые эмуляции не считаются хранилищем.

| Ключ localStorage | Содержимое | Предложение для будущей синхронизации |
| --- | --- | --- |
| `trainer-prototype:appointments:v1` | `SessionRepository`: version, sessions (участники, программа, статус, запрос переноса и история), созданные clients | Серверные записи с версиями; миграция после проверки |
| `trainer-prototype:journal:v1:<sessionId>` | Снимки программ по участникам, подтверждённые подходы, черновики, заметки с shared, дата/время занятия, finished и временные метки | Подходы и заметки как отдельные сущности; черновики локально до подтверждения |
| `trainer-prototype:resume-journal:v1` | Идентификатор свёрнутого журнала | Предпочтение конкретного устройства |
| `trainer-prototype:exercises:v1` | version, items: name, group, bodyweight, unit? | Личная библиотека тренера со стабильными ID и нормализованным именем |
| `trainer-prototype:client-programs:v1` | version 2, byClient → название программы → baseName, exercises, updatedAt (version 1 с одной копией читается) | Версии личных программ с отдельными ID, связью с шаблоном |
| `trainer-prototype:calm:v1` | Независимые boolean trainer/client | Предпочтение пользователя; перенос между устройствами обсуждается |
| `trainer-prototype:field:v1` | version, events: попытки, время, текст, пункты, ошибки, удаления; только при field=1 | Исследовательский экспорт; не включать автоматически в рабочую синхронизацию |

**Палитра не хранится в localStorage.** `js/visual.js` читает `?palette=`;
по умолчанию ink. `?visual=`, `?calm=1`, `?field=1`, `?now=` — параметры демо.
Не добавляем выдуманный ключ палитры ради соответствия первоначальному списку плана.

Демо-тренер, исходные клиенты, шаблоны и упражнения лежат в `data.js`.
Состояния оплаты, посещения, часть приглашений и UI живут в памяти Store;
они не становятся долговременными данными только от добавления сервера.
Это отдельная область миграции, не готовый бухгалтерский контур.

Ключи appointments/journal/resume имеют общий префикс с исходным прототипом.
Два пути на одном origin используют одно browser-хранилище. Для исследования
использовать отдельный профиль/доверенный origin. Обособление демо-данных —
отдельное решение, здесь ключи не переименованы.

## Сущности и связи

| Сущность | Идентичность и связи |
| --- | --- |
| Тренер | trainerId; владелец клиентов, библиотеки, шаблонов, расписания |
| Клиент | clientId + trainerId; связь с учётной записью после принятия приглашения |
| Занятие | sessionId + trainerId; время, часовой пояс, участники clientId; personal/group |
| Запрос переноса | requestId + sessionId + автор; исходный и предложенный интервал, версия, решение |
| Шаблон программы | programId + trainerId; упражнения, версия; имя не является идентификатором |
| Личная программа | clientProgramId + clientId + baseProgramId/version; собственные упражнения и версия |
| Журнал | journalId + sessionId; снимки планов участников, состояние завершения |
| Упражнение журнала | journalExerciseId + journalId + clientId; связь с библиотекой, происхождение замены |
| Подход | setId + journalExerciseId; вес, повторы/секунды, автор, версия; пустота не равна нулю |
| Заметка | noteId + journalId + clientId; текст, shared=false по умолчанию, автор, версия |

У занятия может быть несколько участников; у каждого своя программа и набор
результатов. Изменение личной программы не переписывает снимок в старом журнале.
Удаление упражнения из библиотеки сохраняет ссылку/снимок в истории.
Текущая модель прототипа — по одной личной копии на каждую программу клиента
(«Низ А», «Верх Б» и занятия без программы хранятся отдельно). Что делать с копией
при смене шаблона, остаётся решением владельца до проектирования серверной схемы.

## Требования к будущему решению

- В зале без сети доступны заранее загруженные занятия, программы и предыдущие
  подходы. Запись немедленно сохраняется локально. Недоступную историю не выдаём за пустую.
- После восстановления сети подтверждённые операции отправляются повторяемо:
  одна операция с одним ID не создаёт второй подход, перенос или списание.
- Два устройства тренера показывают состояние отправки и не затирают друг друга.
  «Сохранено на устройстве» и «Синхронизировано» — разные состояния.
- Клиент получает только свои занятия, результаты и shared-заметки. Частный текст
  не должен попасть в ответ API или клиентский кэш, даже если скрыт интерфейсом.
- Права проверяются на сервере по учётной записи и trainerId/clientId. Переключатель
  роли в прототипе не является механизмом безопасности.
- Потерянный телефон: восстановление подтверждённых сервером данных после входа;
  несинхронизированные записи недоступного телефона автоматически восстановить нельзя.
- Резервные копии проверяются восстановлением. Нужны экспорт, срок хранения,
  удаление учётной записи и понятная процедура смены устройства.

## Предлагаемая схема обмена — пока не утверждена

Локальная база (например, IndexedDB) хранит рабочие данные и очередь операций.
Операция содержит operationId, entityId, baseRevision, deviceId, payload и локальное
время. Сервер проверяет владельца и версию, применяет операцию один раз, возвращает
новую ревизию и серверное время. Клиент удаляет из очереди только подтверждённое.
Локальное время помогает наблюдению, но не определяет победителя конфликта.
Первый запуск без сети показывает отсутствие загруженных данных.

Миграция: сделать экспорт исходного браузера → проверить версии → показать сводку
импорта → загрузить под выбранного владельца → подтвердить количество записей.
Повторный импорт с теми же ID должен быть безопасен. Повреждённые данные сохранять
для ручного разбора, а не заменять демо-значениями. Удалять старые ключи можно только
после подтверждённого импорта и согласованной политики резервирования.

## Если один журнал изменён на двух устройствах

Предложение для обсуждения, не реализованное правило:

| Ситуация | Возможное поведение |
| --- | --- |
| Добавлены разные подходы с разными ID | Объединить; сохранить порядок и источник |
| Изменён один и тот же подход | Сохранить обе версии, показать тренеру вес/повторы и устройство; попросить выбрать |
| Упражнение заменено на одном устройстве, подход дописан на другом | Сохранить подход в прежнем упражнении, не переносить молча; показать конфликт структуры |
| На одном завершили журнал, на другом осталось редактирование | Сохранить черновик второй стороны; предложить явное исправление завершённого журнала |
| Удаление против редактирования | Использовать отметку удаления; новую правку не терять до разбора |
| Одновременно открыли и закрыли заметку клиенту | До разрешения выдавать клиенту закрытый вариант; старую уже доставленную копию нельзя гарантированно отозвать с офлайн-устройства |
| Два переноса одного занятия | Проверить ревизию расписания, сохранить одно согласованное время и отклонить устаревшую операцию с объяснением |

Автоматическое «последняя запись победила» просто, но может молча потерять подход.
Для прототипа уже есть блокировка записи устаревшей вкладки в расписании и журнале;
это защита локального браузера, не межустройственная синхронизация. Для личных программ
и библиотеки аналогичной блокировки сейчас нет.

## Варианты хранения вне браузера

Цены проверены по официальным страницам 28.09.2026; это отправная точка, не смета.
Стоимость в тенге зависит от курса, налогов и оплаты поставщика. Расчёт должен включать
разработку, резервирование, поддержку и число операций, а не только цену базы.

| Вариант | Цена и эксплуатация | Данные и офлайн | Плюсы / ограничения для частного тренера в Казахстане |
| --- | --- | --- | --- |
| Supabase Cloud | Free для эксперимента; Pro от $25/мес, доплаты по ресурсам. [Тарифы](https://supabase.com/pricing) | Postgres; выбирается основной регион. Для предложенной схемы потребуется локальная очередь и обработка конфликтов | Удобны связи расписания, клиентов и программ. Фиксированная стартовая подписка может быть существенна для одного тренера. В опубликованном списке регионов Казахстана нет; расположение и резервные копии нужно согласовать до выбора. [Регионы](https://supabase.com/docs/guides/platform/regions) |
| Firebase / Cloud Firestore | Есть бесплатная квота; далее оплата операций, хранения и трафика. Частые чтения и повторные подключения влияют на стоимость. [Биллинг](https://firebase.google.com/docs/firestore/pricing) | SDK поддерживает офлайн-кэш и последующую синхронизацию; при конфликте одного документа действует last-write-wins. [Офлайн](https://firebase.google.com/docs/firestore/manage-data/enable-offline) | Быстрее получить базовый офлайн-обмен, но это не решает описанные конфликты журнала. Регион выбрать из официального списка и проверить доступность/задержку на местных сетях. [Регионы](https://firebase.google.com/docs/firestore/locations) |
| Свой API + Postgres на выбранном хостинге | Смета от поставщика: сервер + диски + резервные копии + мониторинг + работа сопровождающего. Фиксированную цену без конфигурации не назначаем | Размещение в выбранной стране при наличии подходящего поставщика; локальную очередь и синхронизацию разрабатываем сами | Больше контроля над размещением и восстановлением, но кто-то должен обновлять сервер и разбирать сбои. Для одного тренера поддержка может стоить дороже инфраструктуры. Альтернатива — самостоятельное размещение Supabase; ответственность за эксплуатацию также остаётся у владельца. [Self-hosting](https://supabase.com/docs/guides/self-hosting) |

Регион не означает автоматически выполнение всех требований к персональным данным.
Владелец должен определить допустимое размещение основной базы, бэкапов, логов и
обработки речи с профильным специалистом до загрузки реальных клиентских данных.
Этот документ не устанавливает юридическую допустимость конкретного поставщика.

## Вопросы владельцу продукта

1. Какой месячный бюджет на сервисы и какой бюджет на сопровождение? Сколько
   тренеров, клиентов и записанных подходов ожидается в первом пилоте?
2. Какие данные разрешено хранить за пределами Казахстана? Где должны находиться
   резервные копии и кто подтверждает требования к размещению?
3. Чем подтверждается личность тренера и клиента? Как восстановить доступ,
   принять приглашение и отозвать потерянное устройство?
4. Как долго приложение должно работать без сети? Что заранее кэшируем на телефоне?
5. Принимается ли предложенная политика конфликтов? Кто и в какой момент
   разрешает конфликт уже завершённого журнала?
6. Одна текущая программа клиента или несколько чередующихся? Как назначение
   нового шаблона взаимодействует с уже созданной личной копией?
7. Нужен ли клиенту доступ к черновому журналу или только к завершённому?
   Как быстро должно распространяться закрытие ранее открытой заметки?
8. Каковы сроки хранения, требуемое время восстановления и допустимая потеря
   последних несинхронизированных записей? Кто проверяет резервные копии?
9. Где и сколько храним полевые JSON после исследования? По умолчанию в рабочую
   синхронизацию они не включены; иной вариант требует отдельного решения.

После ответов можно сравнить варианты на одном сценарии с двумя устройствами,
потерей сети и конфликтом подхода. До этого поставщик не выбран, SDK и серверный
код не добавляются. Пилотная проверка продукта описана в [протоколе зала](research/gym-test.md).
